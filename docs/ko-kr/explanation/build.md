`bmad-build`는 모든 개발 작업에 사용하는 표준 구현 워크플로입니다. 자유 형식의 의도나 이슈부터 계획이 끝난 스토리까지 무엇이든 입력으로 받아, 안전이 허용하는 범위에서 사람의 개입을 최소화하며 코드를 변경합니다.

상위 계획은 선택 사항이며 상황에 따라 달라집니다. 명확한 변경은 바로 시작하면 됩니다. 큰 이니셔티브라면 PRD, UX 설계, 아키텍처, 에픽, 스토리, 준비도 결과, 스프린트 계획을 갖춘 채 시작할 수 있습니다. 이런 산출물은 다른 개발 워크플로를 고르는 기준이 아니라 구현 컨텍스트를 보강하는 자료입니다.

계획된 스토리가 Build로 넘어와도 해당 스토리는 제품 요구와 인수 기준을 담은 상위 컨텍스트로 유지됩니다. Build는 현재 실행에 대한 별도 기록을 만들어 스토리를 대체하지 않으면서 구현 결정과 리뷰 발견 사항을 추적합니다.

모델은 체크포인트 사이에서 더 오래 실행됩니다. 사람의 판단 없이는 안전하게 계속할 수 없거나 최종 결과를 검토할 때만 다시 사람을 부릅니다.

![Build 워크플로 다이어그램](/diagrams/build-diagram.png)

## 왜 필요한가요?

사람이 개입하는 단계는 필요하지만 비용이 큽니다.

현재 LLM은 여전히 예측 가능한 방식으로 실패합니다. 의도를 잘못 읽거나 빈틈을 자신 있는 추측으로 채웁니다. 관련 없는 작업으로 흐르고 잡음 많은 리뷰 결과를 내놓기도 합니다. 반대로 사람이 계속 개입하면 개발 속도가 느려집니다. 사람의 주의력이 병목이 됩니다.

`bmad-build`는 이 절충점을 다시 조정합니다. 안전하게 자율 실행할 수 있을 만큼 작업 범위를 명확히 정한 뒤에는 모델이 더 긴 구간을 감독 없이 실행하도록 맡깁니다.

## 핵심 설계

### 1. 먼저 의도를 하나의 목표로 정리합니다

워크플로는 사람과 모델이 요청에 담긴 의도를 하나의 일관된 목표로 정리하면서 시작합니다. 입력은 거친 의도 표현이어도 됩니다. 다만 자율 실행을 시작하기 전에는 실행할 수 있을 만큼 작고 명확하며 모순이 없어야 합니다.

의도는 몇 마디 문구, 버그 추적기 링크, 계획 모드 출력, 채팅 세션에서 복사한 텍스트, BMad의 에픽 및 스프린트 산출물에서 가져온 계획된 스토리 등 여러 형태로 들어올 수 있습니다. 워크플로는 기존 상위 컨텍스트를 활용해 안전한 구현에 필요한 빈틈을 메웁니다.

이 워크플로는 사람의 통제를 없애지 않습니다. 대신 사람이 개입할 시점을 중요한 몇 단계로 줄입니다.

- **의도 명확화** - 정돈되지 않은 요청을 숨은 모순이 없는 하나의 일관된 목표로 바꿉니다
- **사양 승인** - 합의해 확정한 내용이 실제로 만들어야 할 올바른 결과인지 확인합니다
- **최종 결과 검토** - 마지막에 결과를 받아들일지 사람이 결정하는 핵심 체크포인트입니다

### 2. 가장 작고 안전한 경로를 선택합니다

목표가 명확해지면 워크플로는 한 번에 처리할 수 있는 변경인지, 더 체계적인 경로가 필요한지 판단합니다. 작고 영향 범위가 없는 변경은 바로 구현할 수 있습니다. 그 밖의 작업은 모델이 더 오래 자율 실행해도 범위를 벗어나지 않도록 계획을 거쳐 기준을 분명히 세웁니다.

### 3. 감독을 줄이고 더 오래 실행합니다

경로를 정한 뒤에는 모델이 더 많은 작업을 스스로 수행할 수 있습니다. 더 체계적인 경로에서는 모델이 승인된 사양을 경계로 삼아 더 적은 감독 아래 실행됩니다. 이것이 설계의 핵심입니다.

### 4. 알맞은 계층에서 실패를 진단합니다

의도를 잘못 이해해 구현이 틀렸다면 코드를 고치는 것만으로는 해결되지 않습니다. 사양이 약해서 코드가 틀린 경우도 diff만 고쳐서는 안 됩니다. 이 워크플로는 실패가 어느 계층에서 시작됐는지 진단한 뒤 그 계층으로 돌아가 다시 생성하도록 설계됐습니다.

리뷰 발견 사항을 보고 문제가 의도, 사양 생성, 로컬 구현 중 어디에서 생겼는지 판단합니다. 정말 로컬에 국한된 문제만 로컬에서 수정합니다.

### 5. 필요할 때만 사람을 다시 부릅니다

의도 인터뷰에는 사람이 참여하지만 반복 체크포인트와는 성격이 다릅니다. 워크플로는 반복 체크포인트를 최소화합니다. 처음 의도를 구체화한 뒤에는 판단 없이는 안전하게 계속할 수 없을 때와 최종 결과를 검토할 때 주로 사람이 다시 참여합니다.

- **불명확한 의도 해소** - 리뷰에서 워크플로가 의도를 안전하게 추론할 수 없었다는 사실이 드러나면 사람이 다시 개입합니다

그 밖의 작업은 더 길게 자율 실행할 수 있습니다. 이는 의도적인 절충입니다. 예전 방식은 지속적인 감독에 사람의 관심을 더 많이 요구합니다. Build는 모델을 더 신뢰해 맡기되, 사람의 판단이 가장 큰 효과를 내는 순간에만 집중하도록 합니다.

## 리뷰 시스템이 중요한 이유

리뷰 단계는 버그만 찾는 곳이 아닙니다. 작업 흐름을 끊지 않으면서 문제가 생긴 계층을 찾아 그곳에서 고치게 하는 역할도 합니다.

이 워크플로는 하위 에이전트를 생성할 수 있거나, 적어도 명령줄에서 다른 LLM을 호출하고 결과를 기다릴 수 있는 플랫폼에서 가장 잘 작동합니다. 플랫폼이 이를 기본으로 지원하지 않는다면 해당 기능을 수행하는 스킬을 추가할 수 있습니다. 메인 대화의 컨텍스트를 받지 않은 하위 에이전트는 리뷰 설계의 핵심 요소입니다.

에이전트 리뷰는 흔히 두 가지 방식으로 잘못됩니다.

- 발견 사항이 너무 많아 사람이 잡음을 직접 걸러야 합니다.
- 관련 없는 이슈를 끌어와 현재 변경의 흐름을 깨고 매번 즉석 정리 작업으로 번집니다.

Build는 리뷰를 분류 작업으로 다뤄 두 문제를 해결합니다.

어떤 발견 사항은 현재 변경에 속하지만 그렇지 않은 것도 있습니다. 현재 작업과 인과관계가 없는 부수적 이슈라면 즉시 처리하지 않고 미룰 수 있습니다. 이렇게 해야 실행 범위를 지키고 무작위 곁가지에 사람의 주의력을 빼앗기지 않습니다.

분류가 언제나 완벽하지는 않습니다. 그래도 괜찮습니다. 가치가 낮은 리뷰 댓글 수천 개로 사람을 압도하는 것보다는 일부 발견 사항을 잘못 판단하는 편이 대체로 낫습니다. 이 시스템은 모든 문제를 빠짐없이 찾는 것보다 신호의 품질을 우선합니다.
