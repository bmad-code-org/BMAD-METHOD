`bmad-project-context`는 코드만으로는 AI 에이전트가 알 수 없는 모든 정보를 관리합니다. 아키텍처가 지금과 같은 형태인 이유, 의도적으로 정한 규칙, 조직의 요구 사항, 새 세션이 작업을 시작하기 전에 알아야 할 위험 요소가 여기에 포함됩니다. 자동 생성 문서를 늘리는 대신, 작고 검증된 컨텍스트 시스템으로 이 지식을 유지합니다.

이 설계의 근거는 분명합니다. LLM이 생성한 컨텍스트 문서는 정확도를 낮추고 비용을 높여 에이전트의 성능을 눈에 띄게 떨어뜨립니다. 긴 개요 문서는 불필요한 탐색도 늘립니다. 항상 불러오는 아주 작은 파일, 필요할 때만 읽는 검증된 소규모 항목, 요청할 때마다 도구로 새로 만드는 맵을 함께 쓸 때 가장 잘 작동합니다. 그래서 이 스킬은 코드에서 유추할 수 없는 최소한의 정보만 관리합니다. 코드 자체가 이미 말해 주는 내용은 설명하지 않습니다. 의도적으로 수집하지 않는 정보와 그 이유를 포함한 전체 근거는 [프로젝트 컨텍스트의 이론](project-context-theory.md)을 참고하세요.

## 두 가지 산출물

**커널**(`kernel.md`)은 모든 에이전트 세션에 불러오는 작은 파일 하나입니다. 일반적인 추측과 실제 사용법이 다른 정확한 명령, 생태계 기본값과 다른 규칙, 위험 요소, 반드시 지켜야 하는 조직 요구 사항을 담습니다. 약 150~200개 지침이라는 제한 안에서 우선순위순으로 정리합니다. 모든 줄은 *이 줄을 삭제하면 에이전트의 행동이 달라지는가?*라는 가지치기 테스트를 통과해야 합니다. 작은 프로젝트라면 커널만 있어도 충분합니다.

**번들**은 커널 뒤에 있는 작은 Markdown 항목 디렉터리입니다. 아키텍처 결정의 근거, 규칙을 정한 *이유*, 도메인 사실, 의사결정 이력을 담습니다. 각 항목의 frontmatter(문서 상단 메타데이터)에는 신뢰 상태가 표시됩니다. 사람이 확인했거나 사람의 검토 아래 경로를 확인한 정보는 `verified`입니다. 추론했지만 확인하지 않은 정보와 헤드리스 실행이 작성한 모든 내용은 `generated`입니다. `index.md`만 진입점으로 사용하고 각 항목은 필요할 때만 읽습니다. 한꺼번에 불러오지 않습니다.

두 산출물은 모두 `project_knowledge` 폴더에 저장됩니다. 표준 설치 설정의 기본값은 `docs/`입니다. 규칙에 따라 처리할 수 있는 작업은 유틸리티 스크립트(`context.py`)가 맡습니다. 검증, 인덱싱, 오래된 정보 점검, 저장소 맵 생성, 프로젝트 간 경로 확인을 스크립트가 처리하므로 에이전트가 도구로 확인할 수 있는 사실을 추측할 필요가 없습니다.

## 세 가지 의도

| 의도 | 수행하는 작업 |
| --- | --- |
| **Ingest** | 컨텍스트를 만들거나 새로 고칩니다. 기존 코드베이스에서는 저장소와 문서를 먼저 조사한 뒤, 실제로 알아낼 수 없는 내용만 묻습니다. 새 프로젝트에서는 사양이나 아키텍처 문서 또는 짧은 인터뷰에서 시작합니다. Refresh는 지난 실행과의 차이만 확인하며 처음부터 다시 시작하지 않습니다. |
| **Query** | 번들을 전부 불러오지 않고 질문에 답합니다. 신뢰 메타데이터도 함께 제공합니다. |
| **Audit** | 오래된 정보 점검, 경로 검증, 가지치기 테스트로 정보 집합을 작고 정확하게 유지합니다. 컨텍스트는 줄어들거나 그대로 유지될 뿐 계속 쌓이지 않습니다. |

## 에이전트가 불러오는 방식

처음 실행하면 스킬이 **배치 방식(placement)**을 묻습니다.

- **bmad** — BMad 커스터마이징 배열로 커널을 불러옵니다. 에이전트 파일은 수정하지 않습니다.
- **agent-files** — 스크립트가 루트 및 중첩된 `AGENTS.md` 파일에 관리형 `<!-- bmad:context -->` 블록을 유지합니다. 블록 바깥의 내용은 그대로 보존합니다. BMad가 설치되지 않은 경우의 기본값입니다. 이 스킬은 프레임워크 없이도 모든 저장소에서 독립적으로 작동합니다.
- **both** — 배열과 에이전트 파일을 모두 사용하고 서로 동기화합니다.

## 아키텍처와의 관계

결정은 `bmad-architecture`에서 내리고 프로젝트 컨텍스트에서 계속 관리합니다. 아키텍처의 핵심 구조는 가장 중요한 ingest 원본입니다. ingest 과정에서 실제로 의견이 갈리는 결정을 발견하면 스킬이 조용히 결론을 내리지 않고 `bmad-architecture`에서 다뤄야 한다고 안내합니다.

## 이전 두 스킬을 대체

:::note[폐기됨: bmad-document-project 및 bmad-generate-project-context]
이전 두 스킬은 모두 폐기되었으며 이제 이 스킬로 연결됩니다. `bmad-generate-project-context`는 단일 `project-context.md`를 만들었고 `bmad-document-project`는 기존 저장소를 스캔해 문서로 만들었습니다. 기존 트리거 문구는 계속 작동합니다. 기존 `project-context.md`도 계속 불러오며 다음 ingest 때 조사 원본으로 사용합니다. 두 스킬의 핵심 생각, 즉 "눈에 보이지 않는 규칙만 수집한다"는 원칙이 이제 전체 구조의 중심입니다.
:::
