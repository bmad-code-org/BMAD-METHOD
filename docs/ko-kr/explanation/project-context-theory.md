`bmad-project-context`는 다소 불편한 발견에서 출발했습니다. AI 에이전트를 *위해* 작성한 문서 대부분이 오히려 에이전트의 성능을 떨어뜨린다는 사실입니다. 이 문서에서는 이 스킬이 무엇을 왜 수집하는지, 더 중요하게는 무엇을 의도적으로 수집하지 않는지 설명합니다. `bmad-document-project` 또는 `bmad-generate-project-context`에서 넘어왔다면 문서 후반부에서 무엇이 왜 바뀌었는지 정확히 확인할 수 있습니다.

스킬의 *기능*과 실행 방법은 [프로젝트 컨텍스트](project-context.md)와 [사용 가이드](../how-to/project-context.md)를 참고하세요.

## 생성된 문서의 문제

세 가지 발견이 이 설계를 이끌었습니다.

1. **LLM이 생성한 컨텍스트 문서는 에이전트 성능을 눈에 띄게 떨어뜨립니다.** 비용은 더 들면서 정확도는 낮아집니다. 생성된 개요는 코드를 다시 풀어쓴 요약에 불과하며 코드보다 신뢰하기 어렵습니다. 세부 사항을 놓치고 코드가 바뀌는 순간 낡습니다. 에이전트는 직접 확인하는 대신 문서를 믿게 됩니다.
2. **항상 불러오는 컨텍스트의 모든 줄은 매 세션마다 비용을 발생시킵니다.** 2,000줄짜리 컨텍스트 파일은 "철저한" 문서가 아닙니다. 앞으로 수행할 모든 작업에 계속 붙는 비용입니다. 그중 대부분은 문서가 없어도 에이전트가 올바르게 처리했을 내용입니다.
3. **잘못된 컨텍스트는 컨텍스트가 없는 것보다 나쁩니다.** 문서가 없는 에이전트는 탐색해서 사실을 찾아냅니다. 오래된 문서가 있는 에이전트는 그 내용을 확신하며 잘못된 길로 갑니다. 오래된 정보는 겉모습의 문제가 아니라 실패를 만드는 원인입니다.

결론은 다음과 같습니다. 가치 있는 정보 집합은 **코드에서 유추할 수 없고 검증된 사실의 최소 집합**입니다. 에이전트가 코드를 읽어도 알 수 없는 내용은 모두 포함하되, 코드에서 알 수 있는 내용은 하나도 넣지 않습니다.

## 포함할 가치가 있는 정보

모든 줄에는 **가지치기 테스트**를 적용합니다. *이 줄을 삭제하면 에이전트의 행동이 달라지는가?* 코드에 이미 드러나 있거나 생태계의 기본값이라서 문서가 없어도 에이전트가 올바르게 행동한다면 그 줄은 잡음입니다. 다음과 같은 정보만 테스트를 통과합니다.

- **당연해 보이는 명령이 실패하는 경우.** 잠금 파일을 의도적으로 Git에서 제외했기 때문에 `npm ci`가 아니라 반드시 `npm install`을 사용해야 하는 경우입니다. 에이전트는 파일이 없다는 사실만 보고 "의도적으로" 제외했다는 점을 유추할 수 없습니다.
- **기본값과 다른 규칙.** 차이가 있는 부분만 기록합니다. "Conventional Commits를 사용한다"는 한 줄은 가치가 있지만 "새 코드에 테스트를 작성한다"는 내용은 그렇지 않습니다. 에이전트가 이미 그렇게 해야 한다고 알고 있기 때문입니다.
- **위험 요소.** 두 번의 마이그레이션보다 오래된 문서 폴더, 작동하는 것처럼 보이지만 깨진 워크플로, 함께 사용하면 안 되는 서로 다른 두 세대의 설정 변수 등이 해당합니다. 이런 사실을 모르면 에이전트는 확신을 갖고 잘못된 작업을 합니다.
- **의사결정 근거.** 아키텍처가 지금과 같은 형태인 *이유*입니다. 코드는 형태를 보여주지만 그 이유는 알려주지 않습니다. 아키텍처 결정은 `bmad-architecture`에서 내리고 프로젝트 컨텍스트에서 계속 관리합니다.
- **조직 요구 사항과 도메인 사실.** 저장소 어디에도 존재하지 않는 정보입니다.

수집한 내용은 **사실로 기록하기 전에 검증**합니다. 조사한 주장은 코드와 대조합니다. 신뢰 사다리에서 코드와 설정은 기준이 되는 사실입니다. 기존 문서는 검증 전까지 신뢰하지 않습니다. 그다음 사람이 확인합니다. 모든 항목에는 신뢰 상태(`verified` 또는 `generated`), 출처, 검증 날짜가 포함됩니다. 누구도 확인하지 않은 주장은 `generated`로 저장합니다. 추론임을 드러내고 사실인 것처럼 꾸미지 않습니다.

## 의도적으로 수집하지 않는 정보

무엇을 비워 두는지가 이 설계의 핵심입니다. 제외하는 항목에는 각각 이유가 있습니다.

| 수집하지 않는 정보 | 이유 |
| --- | --- |
| **코드가 이미 말해 주는 내용** | 에이전트는 소스 요약보다 소스 자체를 더 잘 읽습니다. 바꿔 쓴 설명을 추가하면 원본은 정확한데 복사본만 낡아 가는 문제가 생깁니다. |
| **저장소 구조와 파일 맵** | 구조는 커밋마다 달라져 저장된 맵이 가장 빨리 낡습니다. 에이전트는 이미 가진 도구로 몇 초 안에 최신 구조를 유추할 수 있습니다. |
| **개요와 둘러보기 문서** | 대표적인 생성 산출물이자 측정된 성능 저하의 원인입니다. 긴 개요는 불필요한 탐색과 근거 없는 확신을 늘립니다. 커널의 역할은 독자를 안내하는 것이 아니라 행동을 바꾸는 것입니다. |
| **생태계 기본값** | LLM은 일반적인 Node, Python, Go 프로젝트의 작동 방식을 이미 압니다. 기본값을 다시 설명하면 에이전트가 처음부터 알고 있던 내용을 가르치는 데 예산을 씁니다. |
| **이력과 편집 과정 설명** | "X 때문에 Y를 제거했다" 같은 서술은 금지합니다. 이력은 Git과 memlog가 관리합니다. 항목에는 현재의 사실만 적습니다. 대체 관계는 이야기가 아니라 날짜가 있는 frontmatter(문서 상단 메타데이터) 필드로 기록합니다. |
| **검증하지 않은 추론을 사실처럼 표현한 내용** | 확인하지 않은 내용은 `generated`로 표시합니다. 신뢰 필드가 계약입니다. `verified`는 사람이 검증에 참여했다는 뜻입니다. |
| **사용자용 문서** | 튜토리얼, 설정 가이드, 참조 사이트는 사람을 위한 별도의 산출물이며 규칙도 다릅니다. 이 스킬은 오래된 사용자 문서를 위험 요소로 표시할 수 있지만(예: "이 주제는 docs/를 신뢰하지 말 것"), 직접 작성하거나 교체하지 않습니다. |
| **지향하는 미래 상태** | 시스템이 앞으로 어떤 모습이어야 하는지는 사양과 아키텍처 문서에 속합니다. 컨텍스트는 현재의 사실을 설명합니다. 에이전트가 미래 목표를 현재 사실로 오인하면 잘못된 결과를 만들 수 있습니다. |

결과가 작은 것은 의도된 설계입니다. 건강한 커널은 화면 하나에 들어옵니다. 실제 저장소의 건강한 번들도 열두 개 안팎의 작은 항목이면 충분합니다. 작은 프로젝트에 커널만 필요한 것은 작업이 덜 끝난 것이 아니라 성공한 결과입니다.

## 컨텍스트는 계속 가치를 입증해야 합니다

이전 모델은 문서를 자산으로 다뤘습니다. 범위가 넓을수록 가치가 크다고 봤습니다. 이 스킬은 컨텍스트를 **계속 가치를 증명해야 하는 부담**으로 봅니다. 오래된 정보 점검에서는 모든 주장의 출처를 저장소와 대조합니다. Audit 의도는 모든 줄에 가지치기 테스트를 적용합니다. 작업을 마쳤을 때 컨텍스트 크기는 같거나 더 작아야 합니다. 읽을 수 있는 코드를 단순히 바꿔 쓴 항목은 삭제합니다. 주장의 출처가 사라지면 새로운 사실에 맞춰 주장을 고치거나 제거합니다. 같은 내용을 여전히 언급하는 다른 문서로 출처를 몰래 바꾸지 않습니다.

## 대체된 두 스킬과의 차이

`bmad-document-project`는 기존 저장소를 스캔해 개요, 소스 트리, 영역별 심층 설명으로 구성된 문서 트리를 생성했습니다. 문서를 자산으로 보는 모델이었지만 증거는 반대였습니다. 결과물은 크고 검증되지 않았으며 만들어지는 순간부터 낡았습니다. 에이전트의 성능을 떨어뜨리는 종류의 컨텍스트였습니다. 다만 *작업 전에 저장소를 이해한다*는 올바른 생각은 ingest 스캔으로 이어졌습니다. 이제 이 스캔은 설명문 생성이 아니라 검증에 사용됩니다. 이전 스킬은 저장소 구조를 설명했지만 새 스킬은 에이전트가 최신 구조를 직접 유추하게 합니다. 코드를 요약해 문서로 남기지도 않습니다.

`bmad-generate-project-context`에는 눈에 띄지 않는 프로젝트별 사실을 작은 규칙 파일 하나에 담는다는 올바른 생각이 있었습니다. 이제 그 생각이 전체 아키텍처가 됐습니다. 이전 방식에는 파일을 검증하고 관리할 체계가 없었습니다. 검증 절차도 없어 생성할 때마다 결과의 신뢰도가 달라졌습니다. 신뢰 표시, 오래된 정보 관리 방식, 유지보수 주기가 없었고 규칙을 정한 *이유*를 담을 공간도 없었습니다. 커널은 기존 파일의 개념을 이어받되 분량 제한을 둔 형태입니다. 번들은 이전에 담을 수 없던 근거를 보관합니다. Ingest와 Audit은 두 산출물을 시간이 지나도 정확하게 유지합니다. 기존 `project-context.md`는 계속 불러오며 다음 Ingest 때 조사 원본으로 사용합니다.

이전 스킬은 더 많은 문서를 작성했고 새 스킬은 더 적은 사실을 관리합니다. 정보는 많기보다 적고 검증된 편이 낫습니다.
